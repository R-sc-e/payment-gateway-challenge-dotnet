# Payment Gateway

A small .NET 8 API that validates card payment requests, forwards valid requests to the supplied acquiring-bank simulator, and retains safe payment details for retrieval.

## Run the service

The simplest option starts both the gateway and simulator in containers:

```bash
docker compose up --build
```

The API is available at `http://localhost:5000`, with Swagger UI at `http://localhost:5000/swagger`. The simulator remains available at `http://localhost:8080`.

To run the API from the SDK instead:

```bash
docker compose up bank_simulator
dotnet run --project src/PaymentGateway.Api
```

The bank base URL and timeout can be overridden using `AcquiringBank__BaseUrl` and `AcquiringBank__TimeoutSeconds`.

## API

### Process a payment

`POST /api/payments`

```json
{
  "cardNumber": "2222405343248877",
  "expiryMonth": 7,
  "expiryYear": 2031,
  "currency": "GBP",
  "amount": 1050,
  "cvv": "123"
}
```

A successfully processed bank response returns `200 OK`:

```json
{
  "id": "52f12a23-9499-4d33-b3f6-b6d24e8b4375",
  "status": "Authorized",
  "cardNumberLastFour": "8877",
  "expiryMonth": 7,
  "expiryYear": 2031,
  "currency": "GBP",
  "amount": 1050
}
```

### Retrieve a payment

`GET /api/payments/{id}` returns the same safe representation, or `404 Not Found` if the ID is unknown.

| Scenario | Status |
| --- | --- |
| Bank authorizes or declines a valid request | `200 OK` |
| Request is missing, malformed, expired, or otherwise invalid | `400 Bad Request` |
| Payment ID is unknown | `404 Not Found` |
| Bank is unavailable, times out, or violates its contract | `502 Bad Gateway` |
| Unexpected gateway failure | `500 Internal Server Error` |

Errors use `application/problem+json`. Rejected requests include `paymentStatus: "Rejected"`, field-level errors, and a trace ID. Invalid requests are never sent to the bank.

## Validation assumptions

- Card numbers contain 14–19 ASCII digits.
- Expiry month is 1–12. A card remains valid until the end of its stated expiry month; UTC is used for the comparison.
- Supported currencies are exactly `GBP`, `USD`, and `EUR`.
- Amount is a positive integer in the currency's minor unit.
- CVV contains 3–4 ASCII digits and is modeled as a string to preserve leading zeroes.

These rules intentionally stay close to the assessment brief. No Luhn check, currency normalization, or undocumented maximum amount has been added.

## Design

The controller owns HTTP concerns, `PaymentRequestValidator` owns local rejection rules, and `PaymentService` coordinates the bank and repository. The bank client and repository are the two replaceable boundaries. This gives focused tests without adding layers that the exercise does not need.

The repository is an in-memory `ConcurrentDictionary`, as permitted by the brief. It stores only the last four card digits and never stores the PAN, CVV, or bank authorization code. IDs are generated by the gateway rather than coupled to a bank response.

The typed bank client has a configurable timeout and validates the bank response. Automatic retries are deliberately omitted because processing a payment is not safely retryable without an idempotency contract.

## Observability and health

Logs are structured and exclude card and CVV data. ASP.NET and outgoing HTTP traces propagate W3C trace context. OpenTelemetry records request/runtime instrumentation and low-cardinality payment outcome, rejection, bank-failure, and latency metrics.

The console exporter is enabled in Development and can be controlled with `Observability__ConsoleExporter`. Production systems would normally configure an OTLP exporter and collector rather than write spans and metrics to stdout.

- `GET /health/live`
- `GET /health/ready`

Compose waits for the simulator before starting the gateway and health-checks both containers.

## Tests and coverage

```bash
dotnet test PaymentGateway.sln --configuration Release
```

If .NET 8 is not installed locally, the Docker test stage provides the same check:

```bash
docker build --target test .
```

Tests cover validation boundaries, controlled-time expiry scenarios, exact bank JSON, authorized and declined paths, dependency failures, concurrent storage, Problem Details, sensitive-data masking, and the complete HTTP flow. CI enforces at least 85% line and branch coverage and uploads the Cobertura report.

## Production considerations

A production gateway would additionally need authenticated merchant identity and authorization, durable encrypted storage, idempotency keys, secret management, rate limiting, audit controls, an OTLP telemetry pipeline, and a carefully designed retry/reconciliation strategy. Those concerns are documented rather than implemented to keep this exercise focused on its stated requirements.
